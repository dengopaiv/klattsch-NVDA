# 16. Stage 4 — `kl_token.c`

Stage 4 of the [C rewrite](REWRITE.md): the tokenizer. Branch `stage4-token`,
code in `csrc/kl_token.{h,c}` and `csrc/kl_norm.{h,c}`, driven by
`goldens/cases-text.bin` and verified by `tools/verify-stage4.mjs`.

Back to **Tier 1** after stage 3 — no tolerance anywhere. The stage table
called this one "small, low risk". It was neither, and the reason is one
method call.

## 16.1 The stage is mostly `normalize()`

`tokenize()` begins:

```js
const source = normalize(rawInput);
```

and `normalize()` begins `input.normalize('NFKC')`, which is all of Unicode.
That is the whole stage in one line: the tokenizer's grammar is nine anchored
regular expressions over ASCII, and the thing in front of it is a full Unicode
normalization form.

Three ways out were available: link a normalization library, implement NFKC,
or implement a subset and bound what the subset costs. The third was taken,
and the bound is measured rather than assumed.

### What NFKC actually moves

| | |
|---|---|
| Code points scanned | 1,112,064 |
| NFKC moves | **4,965** |
| …to something entirely ASCII | 1,440 |
| …to something partly ASCII | 234 |
| …expanding past one UTF-16 unit | 1,220 (longest 18, U+FDFA) |

4,965 singleton mappings is a table, not a library: `csrc/kl_norm_data.c` is
4,965 entries and a 6,986-unit pool, generated by `tools/build-norm-c.mjs`
from the same ICU that backs `String.prototype.normalize` in the reference.
Generating it from the reference's own source of truth is the argument that
made stage 2's bank table safe, reused.

### Why leaving out composition is safe, and not a hope

A singleton table is not NFKC. Real NFKC also does canonical decomposition,
canonical reordering by combining class, and recomposition. None of that is
here, so the question is what it can cost — and the answer is exactly
measurable:

| | |
|---|---|
| Code points with a multi-character NFD (i.e. composition targets) | 12,236 |
| …that are ASCII | **0** |
| …that are whitespace | **0** |
| ASCII code points moved by NFKC or NFD at all | **0** |

Composition can therefore never produce a character this grammar reads, and
ASCII input is a fixed point of normalization. Reordering only permutes
combining marks, which are neither ASCII nor whitespace.

The residue is real and worth stating plainly: for an input containing a
combining mark, the **`text` field of an `unknown` token** may hold different
bytes than the reference would give it. `A` + U+0301 is one token either way
and unknown either way; the reference spells it `Á`, this spells it `A` +
U+0301. Nothing else in the token stream can differ, and an unknown token
contributes no sound. If the text front end of phase 3 ever needs true NFKC,
this is the paragraph to come back to.

### The exhaustive check

Because the table is singletons, the test that fits it is one code point at a
time — all of them:

```
Normalization -- exhaustive, every code point
  code points compared               ok     1112064
  stream consumed                    ok     6545460 bytes
  NFKC + strip + homoglyph           ok     identical
```

**1,112,064 code points, zero differences.** That is the whole of Unicode,
compared against V8, including the zero-width strip and the homoglyph fold
that follow.

## 16.2 A character that splits a token in two

NFKC of U+00A8 DIAERESIS is *space + U+0308*. So:

```
"A¨B"  ->  source "A ̈B"  ->  phoneme:A  unknown:"̈B"
```

One input token becomes two, because normalization introduced a space that was
not typed. 67 code points do something like this — U+00A0, U+00A8, U+00AF,
U+00B4, U+00B8, U+02D8… — and every one is a character a user can paste.

This is not a curiosity. It means the tokenizer cannot be written as "split on
whitespace, then normalize each piece": normalization has to happen first and
on the whole input, which is what the reference does and therefore what this
does. `tools/stage4-divergences.mjs` pins the case.

## 16.3 The defect the C declines to copy

`classifyPart` tests the pause table with:

```js
if (part in PAUSE_MS) return { type: 'pause', ms: PAUSE_MS[part] };
```

`in` walks the prototype chain. `PAUSE_MS` is an object literal, so every own
property of `Object.prototype` answers true:

```
  toString         [{"type":"pause","ms":"[Function]"}]
  valueOf          [{"type":"pause","ms":"[Function]"}]
  constructor      [{"type":"pause","ms":"[Function]"}]
  hasOwnProperty   [{"type":"pause","ms":"[Function]"}]
  __proto__        [{"type":"pause","ms":{}}]
```

It does not stop at the tokenizer. `compileString('AA toString AA')`:

```
  totalMs NaN   events 4   warnings []
  atMs    [ 0, 110,
            '110function toString() { [native code] }',
            '110function toString() { [native code] }1100' ]
```

`atMs` has become a **string**, by concatenation, and `totalMs` is **NaN** —
silently, with `warnings` still empty. Eight inputs reach this: the five above
plus `isPrototypeOf`, `propertyIsEnumerable` and `toLocaleString`.

The C tests the three characters the table actually holds, and classifies the
rest as `unknown`. **This is the one deliberate divergence in stage 4**, and
it is asserted on every run in both directions:

```
Divergences -- where the C refuses to copy the reference
  reference still has the defect     ok     8/8
  C classifies them as unknown       ok     8/8
```

If upstream ever fixes this, the first half fails and says so. A divergence
recorded only in a comment is a divergence nobody re-checks — the same
reasoning that made stage 3 keep its unreachable mutation rather than delete
it.

These cases are deliberately **not** in the golden corpus: capturing them
would require `digestTokens` to write a function through `writeDoubleLE`,
which throws. The corpus cannot hold this defect, which is itself a fact about
how bad it is.

## 16.4 `Number()`, and a locale bug avoided

Every numeric field goes through `Number()` on a string the grammar has
already constrained to `[+-]? digits [ . digits ]`.

`strtod()` is the obvious C answer and is the wrong one. It takes the decimal
separator from the C locale, and this code is going to run inside NVDA on
machines where that separator is a comma — where `strtod("3.5")` returns 3 and
stops. A synthesizer whose pitch directives silently truncate on a Finnish or
German desktop is exactly the defect that never appears on the developer's
machine, and it would have been introduced by the most natural translation.

So `kl_parse_decimal` accumulates the mantissa as an integer and scales by a
power of ten. While the mantissa fits in 2^53 and the scale is within 10^22 —
both exactly representable — one IEEE division is correctly rounded, so the
result is bit-identical to `Number()`.

```
Number() -- the one arithmetic step in classifyPart
  grid size                          ok     1368
  exact inside the claimed window    ok     1332/1332
      outside the window, not claimed: 36
```

The first version of the guard reserved room for a 9 rather than for the digit
actually being consumed, which is one digit too conservative and parsed
`9007199254740991` — 2^53−1 exactly — as `9007199254740990`. Caught by the
grid on its first run, which is what the grid is for.

## 16.5 The exit test

✅ Passes on all four toolchains.

```
Tokens -- every case in the corpus, field by field
  cases compared                     ok     714
  tokens compared                    ok     1922
  normalized source matches          ok     all
  every field identical              ok     all
  digest matches the goldens         ok     714/714
```

Compared in both directions on purpose: field by field against a live
`tokenize()`, which says *what* differs, and by digest against
`goldens/cases.json`, which ties the C to the frozen reference rather than to
whatever the JavaScript happens to do today. Stage 1 learned that the first
without the second is a comparison with no reference in it.

### Byte-identical across all four, glibc included

| Toolchain | libm | `tokens.bin` md5 |
|---|---|---|
| MSVC 14.51 | UCRT | `324a0ed162ae5beaaa8d6ad6a3e7056f` |
| clang-cl | UCRT | `324a0ed162ae5beaaa8d6ad6a3e7056f` |
| WinLibs gcc 16.2.0 | UCRT | `324a0ed162ae5beaaa8d6ad6a3e7056f` |

The normalization dump matches across the divide too
(`2614fea3a86ebba8356d531db6f953a7`).

This is worth more than it looks. The 233 `note` cases run through
`noteToHz`, which is `440 * Math.pow(2, (midi - 69) / 12)` — a transcendental,
and therefore the one place stage 4 could have needed a tolerance. Stage 1
found glibc's `sin` disagreeing with the UCRT's on 1.26% of its grid. Here
`pow(2, k/12)` agrees exactly, on every note the grammar can name. **Stage 4
is Tier 1 in fact and not only in intent.**

## 16.6 The mutation suite, and three gaps it found

`tools/stage4-mutations.py` breaks the tokenizer 24 ways. The categories are
chosen against what a translation of a regex cascade gets wrong:

- **cascade order** — `[bank=x]` tried after the generic `[key=value]`, the
  note form disabled. These still produce a token, just the wrong kind, which
  is the failure a "does it parse?" test cannot see.
- **pattern shape** — a character class one member too wide or too narrow.
- **arithmetic** — `Number()` and `noteToHz`.
- **normalization** — the code that reads the generated table. The table
  itself is not mutated; its guard is `build-norm-c.mjs --check`, which is its
  own ctest entry.

Result: **24 of 24 caught**, after closing three genuine corpus gaps.

**`\w` includes the underscore.** No directive key in the corpus had one, so
narrowing the class changed nothing. Closed with `unknown/underscore-key`.

**The stress mark attaches to the *last* phoneme before it.** The corpus's
`stress/separate-mark` is `AA ' AA` — one phoneme in front of the mark, so
searching the token list forwards and backwards give the same answer. Closed
with `stress/mark-after-two` (`AA BB ' CC`).

**The `#` boundary test is nearly dead code.** `#` only starts a comment at
the start of input or after whitespace — but that test is reached only at the
top of the tokenizer's loop, which is where it already just skipped
whitespace. The single way to arrive there with a non-space behind you is
**immediately after a block comment**. Deleting the test changed no golden at
all until `comment/block-then-hash` (`AA /*x*/#tail AA`) was added. The corpus
had `comment/hash-not-at-boundary` and it was not testing what its name says.

The corpus went from 711 cases to **714**; stage 0's own suite still catches
34 of 34 against it.

## 16.7 Two harness defects, and one in the goldens

Consistent with stages 2 and 3, the tooling was wrong more often than the code.

**The mutation runner decoded subprocess output as cp1252.** The verifier
prints token text, some of which is not ASCII, and `U+00A8` killed the reader
thread mid-run — which surfaced as a `HARNESS TIMEOUT` on the *following*
mutation, blaming the wrong line. Fixed with an explicit `encoding='utf-8',
errors='replace'`.

**A patch script reported success without checking.** Three separate edits to
`verify-stage4.mjs` silently did nothing, because the working tree holds CRLF
and the patterns were written with LF. The script printed "added" regardless.
That is precisely the stage 3 lesson — a tool that reports a passing result it
did not verify — arriving again in a different costume. Every edit since
asserts its match count.

**`goldens.mjs` deleted files it did not own.** Capturing the goldens ran
`rmSync(outDir, { recursive: true })` and recreated the directory, which
removed the derived binaries sitting beside the JSON: `schedules.bin`, which
**stage 3** reads, and stage 4's three. So re-capturing the corpus broke the
next stage run with a missing-file error that said nothing about the cause.
Found because stage 4's mutation suite re-captured and then could not find its
own input. It now removes the `*.json` files it writes and nothing else, and
the fix is verified by re-capturing and checking the binaries are still there.

This one had been latent since stage 3 and would have fired on whoever next
extended the corpus.

## 16.8 Step log

**`kl_norm.{h,c}` + generated `kl_norm_data.c`** — NFKC singletons, zero-width
strip, homoglyph fold, in UTF-16 because the reference's `srcStart`/`srcEnd`
are UTF-16 code-unit offsets and the exit test compares them. Verified
exhaustively over 1,112,064 code points.

**`kl_token.{h,c}`** — nine anchored patterns hand-matched rather than a regex
engine, caller-provided storage, no allocation. Clean at `/W4` and `-Wall
-Wextra -Wpedantic -Wshadow -Wconversion` on all four toolchains.

**Exit test passes on four toolchains**, and the dumps are byte-identical
across all four including glibc.

**Mutation suite 24 of 24**, after closing three corpus gaps. Corpus 711 → 714;
stage 0 still 34 of 34. `ctest` 9 of 9.

**Two pre-existing `-Wcomment` warnings fixed** — `banks/*.json` inside a block
comment opens a nested comment, which gcc warns about on every build.

**One deliberate divergence**, §16.3, asserted in both directions every run.
